## 修正

dev5は推論の開始前・完了時に元の受付主体の権限を再検証していました。
しかし推論中の照会で失効を検知しても実行中の要求には記録せず、推論完了前に権限が戻ると候補が生成されました。
19ケースを追加し、修正前はすべて失敗することを確認しました。

dev6では、scene.status / scene.cancel / 同一入力scene.analyzeで検知した未完了要求の失効を永続化します。
CallerId、scope、policy、要求全体のactor/assetRevision、action、targetを検証し、既存の理由コードでrejectedにします。
認可処理の例外・内部取消・不正grant・未知コードはfailed / authorization_unavailableとし、ジョブ結果・台帳へ例外詳細を格納しません。
受付APIの既存のエラーコード・例外伝播は変更しません。
その後の権限復旧・古い並行grant・同一ID再送・別セッション・再起動でも候補は復活しません。

照会間に失効と復旧が完結する場合は、ホスト専用のRevokeRequestAuthorization(callerId, requestId)で通知します。
権限が失効していても認可ホストが通知でき、利用者のCapabilityからは呼べません。
受付済みの対象要求を指定し、影響する要求ごとに失効を通知してから再付与します。
通知された未完了要求はrejected / permission_denied、完了済みなら候補のみ除去して解析履歴を保ちます。
保存失敗はjournal_unavailableとして通知し、新規推論を止めます。反復通知でも保存を確認します。

実行中の失効はバックエンド取消を要求しますが、物理推論が終わるまで枠を保持します。
取消非対応の遅い応答は破棄し、認可の障害自体ではGPU残存処理として隔離しません。
取消済み・期限切れ・世代更新の終端状態、撮影期限、冪等性、完了済み解析履歴は維持します。

公開済みv0.1.3の型、Scene v1 JSON Schema、台帳形式、ハッシュ・IDの計算式は変更しません。
Cosmosだけ0.1.4-dev6へ更新し、既存5パッケージは0.1.3-dev1のままです。
